# Decisions

Settled decisions for Sandkit, newest last. One line each, with the reason.

## Principles

- **AI agents are the primary authors of sandbox code.** When choosing between approaches, prefer whatever agents work with most reliably.
- **Keep it as simple as possible.** No build tools, no installs, no framework machinery.
- **Code reads clearly.** Minimal, elegant and close to self-explanatory, echoing the clarity sandboxes aim for, without growing bigger for the sake of it. Modern plain JavaScript (template literals, `const`/`let`), no build step.
- **Not production.** Size, duplication and bundled dependencies are acceptable; sandboxes are shared among a handful of people, not served at scale.
- **The model is the source of truth; components show state derived from it.** The sandbox's model holds the state and drives every component. A component shows what it is given, and what viewers do in it comes out as events for the sandbox to act on, so no two parts of a sandbox can drift out of step.

## Components

- **A component is a custom element (custom tag), without Shadow DOM.** It's the browser's native "element with an interface" protocol, easy for agents to write, and the tag is the boundary. Shadow DOM's isolation costs simple styling and debugging for a problem sandboxes don't have.
- **Outside follows the protocol; inside can be anything.** Vanilla JS, jQuery, Preact, etc. are all allowed internally.
- **Protocol:** one root element it owns; inputs in (attributes and properties); `CustomEvent`s out, bubbling from the root; a few documented methods; prefixed, documented CSS classes; no globals beyond the tag name; a manifest describing it all.
- **Several instances can share a page.** Each instance keeps its own state; anything that must be unique in the document (ids, radio group names) is generated per instance. Every component has a test with two instances side by side.
- **Names: prefixes are namespaces.** `sb-` is reserved for the Sandkit catalog, which keeps names unique within it. Other authors use their own prefix.
- **Collisions fail loudly.** Each component carries an origin marker. The same script loaded twice is skipped quietly; a different component already using the tag gets a console error explaining how to rename. Renaming is a find-and-replace of the tag in one file, because the tag, classes and style id all start with it.
- **Styling via prefixed classes** (e.g. `sb-id__code`). Sandboxes override them with their own stylesheet.
- **Components never reference each other,** not even as an optional enhancement. A component doesn't know any other component's tag, events or protocol, and its demo loads only itself (plus the shell, which is the environment around demos, not a dependency). Coupling stops things scaling and removes flexibility. Only components explicitly packaged together may know each other, and that should be rare.
- **Extend before adding, and say which.** When a new component is proposed, first ask whether an existing one could do the job by growing its own capabilities, and call it out. If it can, extend it. Make a new component when the job has its own needs, such as a different data shape, layout or options, however similar the two look (`sb-flowchart` beside `sb-graph`, `sb-table` beside `sb-rules`). Either way, nothing is shared between components.
- **Composition happens in the sandbox, through slots.** A component that should accept the sandbox's content offers slots (children marked `slot="..."`), and shows that content without inspecting it. The shell knows no section by name either: the sandbox declares `<sb-theme-settings slot="settings">`.
- **Manifests suggest pairings in a "Works well with" section.** Text only: which components combine well, and how to wire them. Agents read the suggestion and do the wiring; nothing is hard-coded.
- **Components are domain-agnostic.** They give a domain the tooling and never name domain concepts. The sandbox maps its domain onto the component's generic shape (e.g. a stock-out becomes a log entry with `tone: 'bad'`).
- **Each component folder has:** the script, `manifest.md` (the agent-facing contract: purpose, usage, data shape, attributes, properties and methods, events, styling, works well with, notes), `test.html`, and `demo.html`. `sb-log` sets the template.
- **Demos are for people.** Two headed parts: **About**, a short guide, then **Examples**, the component live and configured for contrasting sandboxes. The guide covers what it's for, where it helps, where something else fits better, getting started, and how to make it reveal rather than merely display. It links to the manifest for the full contract. Written warmly and plainly, to help people build sandboxes that help them understand the world.
- **`CATALOG.md`** lists every practice and component in one line, linking to each. Agents read the catalog, then only the practices and manifests they need.
- **Practices are plain instructions** in `practices/`: how and why to do something well (e.g. identifiers). Not formal skills, just markdown read before using the components that support them. They live apart from components because a practice usually spans several. A manifest names the practice its component supports. Reading path for an agent: catalog → practice → manifest → build.
- **Libraries:** bundle a small library only when needed, scoped privately (no globals), and list it in the manifest. Duplicate copies across components are fine.

## Component designs

- **`sb-controls` keeps the clock.** While playing it fires `sb-tick` with how many steps to take; fast speeds batch several steps per tick. Step fires the same event with one step, so a sandbox handles a single event and never writes its own timer. Halting is the model's business: the sandbox sets `running = false`. Setting properties never fires the viewer-action events.
- **`sb-graph` replaces `sb-network`,** covering state machines as well as flow networks: circle or given layouts, loops pointing away from the middle, two-way edges bowed apart, multi-line labels whose lines can be highlighted individually, terminal rings, tones, meters and tokens, framed to fit and never scaled up. Automatic layout waits until a sandbox needs it.
- **`sb-rules` shows which rule applies,** in words as well as colour ("next", "just applied"). Grouping and per-column formatting; a slot per rule lets a sandbox put a richer code in its cell.
- **`sb-chart` never cuts off its data.** `yMin` and `yMax` set the least range to show; data beyond them widens it, and the zero axis stays inside the drawing. Negative values are supported. Reference lines and series take explicit tones rather than colours by position. The latest value of each line is marked, several lines get a legend with their latest values, and the chart draws at its real width so text keeps its size. Pointing reads the values at any moment; `marks` name events; `highlight` brings a line forward or makes a threshold or event stand out, so prose can point at any named part; `current` marks a scrubbed moment, so a chart and a timeline can point at the same time.
- **`sb-panel` lets viewers rearrange a sandbox,** as an opt-in wrapper around any content, so no component knows about docking. Docked is where the sandbox placed it; popping out floats it at the same spot and size, leaving a same-sized placeholder so the page never moves. Floating panels can be dragged, resized, collapsed, made full screen and brought to the front, and stay within reach. With an `id`, each viewer's arrangement is remembered. Desktop and tablet only: phones are out of scope.
- **`sb-plane` draws vectors as data, not as components.** A vector component would need to know the plane's scale and transformation, which is coupling. The plane takes a matrix and a `progress`, blending evenly from the identity, so viewers watch space move (points travel in straight lines, as in 3Blue1Brown's tools; rotations along arcs could be an option later). 2D only: 3D is several times the complexity and will be its own component when a sandbox needs it. Dragging moves objects by the pointer's movement, in their own space.
- **Tabs are generic, and chapters are one use of them.** `sb-tabs` makes a tab for each direct child, titled by its `heading`, and only ever looks at its own children, so tab sets nest without knowing about each other. Hidden panels stay in the page, keeping their state. Remembered per viewer with an `id`. Linking to a tab from the address bar is left for later, as an opt-in, since it touches the page's URL.
- **One `sb-matrix` covers vectors too:** a vector is a matrix with one column. Its value over MathML's static matrices is editing, tones and highlighting, so numbers can point at what they mean. Symbolic expressions stay a separate, later component; the two can light each other up through a page-wide event without knowing about each other.
- **Pointing works through one page-wide event, `sb-highlight`** (`{ ref }`, or `null` when pointing stops), described in the highlighting practice. `sb-id` pills and `sb-math` terms announce and light up; other components keep their own `highlight` properties and the sandbox routes refs to them, so no component listens for things it can't own. A ref names a single thing.
- **Finding and going to a ref is the sandbox's job,** so no component searches the page. Every part a component draws for a thing with an id carries `data-ref` with that id, so one query finds everywhere a thing appears, and the sandbox's `goTo` (in the locating practice) calls `reveal` on whatever holds the place, outermost first. `data-ref` names what a part is; whether it also answers pointing stays each component's business. Cross-references, comments and tours all rest on this.
- **`reveal(ref, place)` makes a part visible and nothing more.** A component that can hide parts opens, expands, switches or pans to it and returns whether it holds it. `place`, the element being gone to, is optional and matters only to components holding the sandbox's content, where a ref may sit in several panels; `goTo` always passes it. Scrolling isn't hiding: `scrollIntoView` already scrolls every box around a part, so a component that only scrolls, such as `sb-table` or `sb-rules`, has no `reveal`. It never selects, fires viewers' events or undoes a viewer's search or filter, since viewers' choices stay theirs: a part a viewer's filter hides isn't found.
- **`sb-xref` lists; it never finds.** The sandbox finds places with `placesOf`, gives them as data, and goes with `goTo` on `sb-go`, so the component never searches the page. Places a viewer's choice hides are listed with the reason rather than undone. Links are the model's to give, grouped by relation; following one starts a new subject, and the trail is the component's own. Its rows carry no `data-ref`, since they are ways to places, not places.
- **`sb-walkthrough` has no `reveal`.** Its steps are what reveal: they outline views and light parts inside them. Reaching into a walkthrough to open one of its steps would turn that around, with one revealer revealing another. Its pointing words are found, but not gone to.
- **`data-ref` is the one thing a component may look for in content it holds.** It's a page-wide convention, like `sb-highlight`, not another component's protocol, so `sb-tabs` can reveal the panel holding a ref without knowing what drew it.
- **Pointing shows, clicking acts.** Hovering or focusing only lights things up, and clears on leaving; a click does something lasting, such as selecting, navigating or stepping. In prose, a dashed underline means point at me and a solid one means click me, and hovering a click word still previews what the click will do. Say which once, near the words. (A word that only acted on click felt broken when pointed at.)
- **Maths is native MathML,** wrapped by `sb-math`: no library, no fonts, export-safe. Parts marked `data-ref` become pointable.
- **Bounded progress is `sb-scrubber`; unbounded is `sb-controls`.** A scrubber has a start and an end to scrub between, plays at a steady pace (`duration` for the whole range), can loop, and names moments with marks. Scrubbing pauses, so the viewer stays in control. It was first called `sb-timeline`; renamed while no sandbox used it, because a timeline is a chart of events, not a control.
- **`sb-callout` sets things apart, like a textbook's boxes.** A small fixed set of kinds (definition, note, tip, question, answer, warning), each with its own title, tone and icon, so readers learn what to expect; `heading` and `tone` cover anything else. Collapsible callouts use the native disclosure element, which suits answers: think first, then reveal.
- **`sb-table` is the general table; `sb-rules` stays the table of rules.** Sorting, search and a model-driven filter, with a count of hidden rows so they never go unnoticed. Its reveal is marking the cells that changed since the rows were last set, matched by `id`, with direction and previous value, so a step shows what it changed. Paging, editing, grouping and column resizing wait until a sandbox needs them.
- **`sb-erd` draws each reference from field to field.** A line starts level with the row that holds the reference and ends level with the field it refers to (or the title, when only the entity is named), so no one guesses which field a line belongs to. References live on fields, so there is no separate list of edges to keep in step. Rows have a fixed height, making every position exact without measuring the page. Positions are given; automatic layout, cardinality and dragging wait until a sandbox needs them.
- **`sb-flowchart` is its own component, not an option of `sb-graph`.** A flowchart has needs a free-form graph doesn't: kinds of step with their own shapes, layout from structure (each step ranked by its longest way in, loops set aside, lanes from each node), right-angled lines that go around steps, and swim lanes running down or across. Layout and routing are worked out along and across the flow and turned into x and y last, so both directions share one logic. It marks where a process is (`active`) and the way it came (`visited`). Wide charts scroll rather than shrink their text.
- **`sb-tree` is for things inside things,** each in one place. Nodes nest through `children`; having `children`, even none, makes a branch. Everything a viewer can do has a property or method (`expanded`, `selected`, `highlight`, `expand`, `collapse`, `reveal`), and events fire only for what viewers do. A highlighted node folded away marks the closed branch that holds it, so pointing never disappears. Keyboard as in the standard tree view.
- **`sb-sequence` plays a conversation.** Participants, lifelines and messages in order (call, reply, async, to oneself) and notes, spaced to fit their labels. `current` marks the message happening now and fades the rest to come, so one property steps a story along. Highlighting or pointing lights what's connected: a participant's messages and notes, a message's participants. Activation bars and fragments (`alt`, `loop`, `opt`) wait until a sandbox needs them.
- **`sb-code` shows a trace; it never runs code.** The sandbox's model records each step as it runs (`{ line, variables, note }`), and the component shows it beside the code, any language or pseudocode, marking the current line and the variables that changed. Colouring is configured as word lists and comment markers (`syntax`), with pseudocode-friendly defaults a sandbox extends for its own DSL; arbitrary regular-expression rules were left out as harder for agents to get right. Stepping backwards is as easy as forwards. Built-in controls move the step and fire `sb-step`, as a scrubber does. Running real JavaScript to produce a trace automatically can come later as a separate tool, keeping the component small and language-free.
- **`sb-stat` keeps score.** A few headline figures, each showing its change since the stats were last set (matched by `id`, as in `sb-table`), coloured by `better` (`higher` or `lower`), so a rise in cases reads as bad and a rise in savings as good. `max` and `target` add a bar with the target marked. The figures' history belongs in a chart.
- **`sb-bars` compares things now; `sb-chart` shows change over time.** Bars are a new component rather than a chart mode, because the data is named values rather than values over time. Across by default, in one shared grid so every bar has the same scale, or up as columns (`orientation="vertical"`); negatives grow away from zero. Columns whose labels don't fit are numbered, with a legend naming them; a bar, its number and its legend entry light up together. Each update shows every bar's change, with a mark where it was, coloured by `better`, as `sb-stat` does. Grouped and stacked bars wait until a sandbox needs them.
- **`sb-grid` is for models across space, cell by cell.** A new component rather than an `sb-matrix` mode: thousands of cells redrawn every tick need a canvas, not a bracketed matrix of numbers. Cells are coloured by `states` (with a legend counting each, and pointing at one showing where its cells are) or a `scale` (a heat map). Painting fires `sb-paint` and never changes the grid itself, so the model stays the source of truth. Changed cells are outlined only on request, as a fire changes hundreds at once.
- **`sb-c4` is one nested model with many views.** The sandbox describes the architecture once, relationships at the depth they really happen, and each view is derived: a boundary round the focus's children, the neighbours they talk to outside it, and every relationship rolled up to the boxes that can be seen, so no level can contradict another. Navigation is a `path` with a breadcrumb; the sandbox can set it or `reveal` any element. A new component rather than an `sb-graph` mode, for its nesting, notation and navigation. Layout is automatic; tracing a flow, an animated zoom and hand-placed positions wait until a sandbox needs them.
- **`sb-wireframe` is written in HTML, not described in data.** HTML already lays out screens and agents write it fluently, where a schema would be a weaker copy to learn; `sb-math` wraps MathML for the same reason. The sandbox owns the markup and writes the model's state into it; the component draws it as a wireframe, shows one `data-screen` at a time, moves on `data-go`, and points at `data-ref` parts. The look is a few `--sb-wireframe-*` colour and font tokens, defaulting to the theme, with the content's own styles kept weak so a sandbox's classes win. Device frames, a hand-drawn look and a map of the screens wait until a sandbox needs them.
- **`sb-walkthrough` tells one story across several views.** Steps are HTML children (`data-step`) shown one at a time; views are children with a `slot`, laid out beside the narration in a few fixed arrangements of one to four, never a grid to configure. Each step names the views to outline (`data-focus`) and the refs to highlight (`data-highlight`); it can't reach into the views, so it reports them in `sb-step` and `current`, and the sandbox passes them on, as with `sb-highlight`. Each view sits in a cell of its own so a popped-out panel's placeholder keeps its place, and the outline is on the view itself so it follows it. Anything else a step sets travels as its own `data-` attributes.
- **`sb-modal` is the browser's own modal dialog, wrapped.** The native `<dialog>` already lies over everything, keeps focus inside, closes on Escape and returns focus, so the component adds only a heading, a body, actions and the reason for closing. A viewer's closing takes effect at once and is reported in `sb-close` (`escape`, `backdrop`, `close`, or a `data-close` value), as tabs switch and then report, so a sandbox never writes the same close handler. A new component rather than an `sb-panel` mode: a panel sits beside the model, a modal takes over until dismissed. Stacked modals, drawers and confirm helpers wait until a sandbox needs them.
- **`sb-json` spotlights paths rather than lines.** Prose talks about fields, so the spotlight is a list of paths written as code reaches them (`order.items[0].price`); each keeps the lines that open and close around it, so the structure stays readable, and line numbers stay the full document's. Runs of other lines fold into gaps a viewer can open, a single line is never folded, and `expanded` shows everything with the spotlight still marked. The property is `spotlight` because elements already have `focus()`. Notes on paths live in the component, shown in a path bar on selecting or pointing, so the data carries its own documentation. A new component rather than an `sb-code` or `sb-tree` mode: it understands the structure it prints. Marking changes between values waits until a sandbox needs it.
- **`sb-image` crops by view, not by cutting.** Places are fractions of the image, so marks survive a sharper copy. The starting `view` shapes the frame, so a crop sits in the page like an image of its own, and viewers can still zoom out to all of it. Marks are boxes and pins; `highlight` takes one, glides to it and dims the rest, so prose steers the eye. Moves the sandbox makes glide and the viewer's follow at once; zooming needs Ctrl or ⌘ so the page still scrolls past an inline image. Clicks report places, so marks are placed by pointing. Touch pinching, a minimap and comparing two images wait until a sandbox needs them.
- **`sb-annotate` marks text with `<mark>`, not offsets.** Character ranges break the moment the text is edited, and agents write HTML fluently, so the sandbox wraps the phrases itself and the notes travel with them as `data-note`. Pointing shows the note in a card just above the line pointed at; clicking pins it, so pointing shows and clicking acts. Kinds colour the marks, and a legend counts them and fades the other kinds when pointed at, so the shape of the evidence shows at a glance. A new component rather than an `sb-id` mode: a pill resolves a code from the model, while a mark annotates the sandbox's own text. Stepping through marks, viewers adding notes, a margin list and overlapping marks wait until a sandbox needs them.
- **`sb-board` shows many things across stages; `sb-flowchart` shows one process and where it is.** A new component rather than a table or flowchart mode: its reveal is where things pile up, so each column counts its cards against an optional `limit` and is flagged when over it, but never refuses a card, since what's allowed is the model's business. Setting `items` marks the cards that moved ("from Picking") or are new, matched by `id`. Dragging, or the arrow keys, fire `sb-move` as a request, as `sb-grid` reports painting, so a model can refuse a move and say why. How long a card has waited is the model's to say, in its `note` and `tone`. Swimlanes, ordering within a column and editing cards wait until a sandbox needs them.
- **`sb-timeline` lays out events; `sb-scrubber` moves through progress.** Times are plain numbers in the sandbox's unit, shown through `format`, so years, days and model steps work alike with no date handling. Rows within a lane are shared out at the sandbox's `view`, estimating label widths rather than measuring them, and stay put while viewers zoom, so nothing jumps under the pointer. `now` fades what's still to come and fills running spans up to it; dragging it only asks, as moving a card on `sb-board` does. Viewers' zooming survives new events until the sandbox sets `view`. Links between events and clustering were left for a sandbox that needs them.
- **`sb-decision-tree` is its own component, not a flowchart or tree mode.** It knows which nodes are questions, answers and outcomes, so it can say what a flowchart can't: the case's value at each question, and which answers not taken would have changed the outcome (any branch from a question the case went on from that leads to another outcome), labelled with where they lead. The model decides the way a case goes and sets `trace`, as `sb-code` shows a trace; the component never evaluates a rule. Counts thicken branches by the cases that took them. Layout is a tidy tree, each outcome its own place across, with room on each branch for its labels. Rule trees only: decision analysis with chances and expected values, each outcome's mix of cases, and editing wait until a sandbox needs them.
- **`sb-statechart` is its own component, not an `sb-graph` mode.** Nesting, parallel regions, pseudo-states and a configuration of many active states need their own data, layout and marks. The machine is written like an XState config, which agents already know. The component shows state and never holds it, but offers `initial()` and `next()`, which work out SCXML semantics and change nothing, since getting exit and entry order and history right is easy to get wrong in every sandbox. So the chart can be the model, for a concept or a small model beside the main one, or be drawn from a model that has states of its own. Its reveal is the last step numbered in order (exits, transitions, entries) and what can happen now, inherited and guarded transitions included. Layout is automatic, in columns within each compound state; eventless and delayed transitions, done events and positions placed by hand wait until a sandbox needs them.
- **`sb-venn` is its own component, about overlap.** No other component knows that a thing in two sets belongs to one region, or what that region is called. Each region has a ref naming exactly the sets it's in (`'a&b'`, `''` for outside), so prose can point at "mammals that lay eggs" as easily as at a set, and the reading line says it in words, "not" included. Empty regions are shown as "none", since an empty overlap is often the finding. Items are sorted by the component, or a sandbox gives `counts` for populations too large to name; either way changes since the last update are marked, as on `sb-board`. Layouts are fixed and symmetric, with region hit-testing done by geometry rather than drawn shapes. Four sets and circles sized by count wait until a sandbox needs them.
- **A component built when the page has loaded builds once,** even if something moves it while the page loads and it's asked twice.
- **Interaction outranks tone.** A selected or active element shows as such even when it also carries a warning tone.

## Sandbox shell and theming

- **The sandbox shell** is the environment around the components: header and settings (later navigation). It's `<sb-shell>` in `shell/`, following the same protocol as components.
- **Theming is its own module,** `shell/sb-theme-settings.js`: tokens, theme state and the Theme settings section. It applies the theme as soon as it loads. The shell and theming talk through a protocol and DOM events, not shared globals.
- **Settings are made of sections.** Any element can be a section (titled by its `heading`); sandboxes add their own with `slot="settings"`. A section with `settingsKey`, `exportSettings()` and `importSettings(data)` is included in the settings file.
- **The header is the shell's top bar, filled through slots.** Children marked `slot="actions"` sit beside the controls; other children are header content (e.g. the goal), shown on one line with More / Less.
- **Header controls: full screen, settings, collapse.** Collapse hides the header behind a small restore button and is remembered per viewer. A sandbox chooses which controls appear with the `controls` attribute.
- **Components are configurable.** Generic but not always applicable features are opt-in or opt-out through attributes or properties at setup.
- **Theming uses CSS custom properties (`--sb-*` tokens).** A theme is a set of token values under `[data-theme="..."]`; switching is one attribute on `<html>`, and everything updates with no re-rendering. Plain CSS, no JavaScript per component.
- **Components always use tokens with a fallback** (`var(--sb-text, #1f2933)`), so they still work without the shell.
- **Standard themes: light and dark,** plus "match system". Sandboxes add their own by defining tokens in their stylesheet and adding them to the `themes` property of `<sb-theme-settings>`.
- **Viewers can customise tokens and save presets** in settings. A preset is a base theme plus only the tokens that differ, stored per viewer in browser storage.
- **Settings export and import as a JSON file** (`{ format: "sandkit-settings", version, sections: { [settingsKey]: data } }`), so viewers can keep a copy or share them. Importing theme presets merges them by id.
- **Canvas-drawn components** listen for the `sb-theme` event on `document` and re-read the tokens.

## Building and distributing sandboxes

- **An AI assistant builds sandboxes; people need no technical knowledge.** The README's Getting started tells them to open an assistant in a new folder and ask for the sandbox they want, pointing it to Sandkit.
- **The assistant's entry point is `practices/building-a-sandbox.md`,** the end-to-end method. `CATALOG.md` lists it first.
- **Sandboxes grow in iterations, never all at once.** Iteration 1 is the model plus chapter 1, rough, with the remaining chapters only planned. Every iteration ends with a handover offering 2–4 named directions, and the next is built only once the person has chosen. Polish goes only to what has survived feedback. (Learned from the first real build, a Turing machine sandbox, which built five polished chapters unseen.)
- **Sandboxes stay lean on testing for as long as they can.** A young model needs no tests. Model tests come once the model has grown enough that a change could quietly break it, a bug returns, or the person asks: plain assertions in `model.test.js`, no library, the cheapest tests there are. The starter lives in the guide rather than the template, so it isn't filled in by default. The interface gets no automated tests unless the person asks or it's truly justified, and checks by hand only when really needed. Sandkit tests its components because it's a shared library; a sandbox's interface is not. The guide assumes nothing about the agent's environment: there may be no browser automation or Node at all, so the model tests run in either Node or a page.
- **Each sandbox's `AGENTS.md` says where it stands:** version, chapters built, chapters planned, the direction chosen and open questions, rewritten every iteration, so the next session can pick it up. (It was first called the Roadmap.)
- **A sandbox keeps a journal of what changed and why** (`JOURNAL.md`), only ever added to, beside where it stands, which is rewritten. History and present have different jobs: one for audit, one for handover.
- **Every journal entry is a version,** by Sandkit's own semantic versioning, pre-1.0 rule included, so there is one rule to learn. Breaking means something someone may have cited or concluded no longer holds. The version identifies the entry; a separate entry code was left out as a second name for the same thing.
- **Retired codes are recorded in the model and answered in `sb-resolve`,** with the version that retired them and what replaced them, so an old pill says where its code went rather than showing as broken. `sb-id` needed no change.
- **In a sandbox with Git, one journal entry is one commit,** its subject starting with the version, and breaking versions tagged. Without Git everything else still works. (Sandkit itself commits only when the author asks.)
- **Components are copied into each sandbox, not installed.** No package manager. The sandbox starts from `templates/sandbox/`, and Sandkit's files go into `lib/sandkit/`, keeping Sandkit's own paths so links between manifests and practices still work. Only scripts, manifests, practices and the catalog are copied; tests and demos stay in Sandkit.
- **`tools/setup.mjs` does the copying in one command, where Node is available.** It is idempotent: it starts a folder from the template if needed (never overwriting the sandbox's own files), copies the shell, catalog, practices and the named components plus any already present, adds their script tags, and writes `SOURCE.md`. Setting up, adding and updating are the same command. It refuses unknown and in-progress components. Copying by hand remains the documented path for agents without Node.
- **No check tool for sandboxes.** A headless-browser checker was considered and dropped: it is interface testing, which sandboxes avoid, and assumes tools the agent may not have.
- **Sandkit, the shell and each component are versioned separately,** by semantic versioning, starting at 0.1.0. Until 1.0, breaking changes raise the minor version. Each has a short changelog, newest first, whose top entry is its version; the version is repeated in its scripts' first lines so a copied file always says what it is (`test/versions` keeps them in agreement). The shell's two scripts share one version. Breaking entries say how to migrate, so an agent can update a sandbox from the changelogs alone. Changelogs are copied into sandboxes with what they describe.
- **Updating a sandbox reads the changelogs between versions.** `SOURCE.md` records every installed version; `setup.mjs` compares installed and new versions and lists every change in between, breaking changes first.
- **`lib/sandkit/SOURCE.md` records where the copies came from** (repo, commit, date, files). Updating means re-copying them. Each sandbox keeps working as it is until someone chooses to update.
- **Agents use components through manifests, never their source.** Every manifest says so; the sandbox's `AGENTS.md` repeats it, and forbids editing `lib/`. To change a component, eject it into the sandbox's own `components/` under a new name.
- **Other libraries work the same way:** a `CATALOG.md`, a manifest per component, their own tag prefix, copied into `lib/<library-name>/`.
- **The shell has a manifest too** (`shell/manifest.md`), since agents don't read its source either.

## Testing

- **Automated regression tests with no dependencies.** Each module has a `test.html` beside it that tests its public contract; open it in a browser to see results.
- **One shared harness,** `test/harness.js` (`test`, `assert`, `assertEqual`, `assertThrows`, `mount`, `nextFrame`, `recordEvents`). Tests never ship inside sandboxes, so sharing it doesn't break component isolation.
- **Each example sandbox has a smoke test** that loads its real page and checks every part rendered, so integration mistakes fail the suite.
- **One command runs everything:** `node test/run.mjs` drives headless Chrome over every `test.html`, with a fresh browser profile per page, runs every `test.mjs` (tests of Node tools) with Node, and exits non-zero on failure. Node is only needed for the runner. A page that reports no results (the browser didn't finish) is retried once; failing tests never are. Each test times out on its own after 3 seconds, so one that hangs fails by name instead of silencing its page.
- **Automated tests never depend on the browser rendering frames.** Headless Chrome under virtual time, like a background tab, can stop rendering, so resize observers and animation frames may never fire. Tests check what each render does; behaviour driven by rendering (such as redrawing on resize) is checked by hand in a real browser. `waitFor` polls for a condition instead of sleeping a fixed time.

## Examples

- **Build example sandboxes first, and develop components around them.** Several examples, deliberately different, so each component is seen from multiple perspectives.
- **Sandbox page scripts declare everything first, then start** in one marked section at the end, so nothing runs before it exists.
- **First example: supply chain** (intuition kind). End-to-end understanding of sourcing, distribution, fulfilment, transport, delivery, click and collect, stock levels, and the problems and solutions involved. Designed as a baseline that others can branch and adapt to their own organisation, potentially towards decision modelling.
- **Third example: checkout architecture** (intuition kind). How a shop's checkout is built, from the parts down to the code and data, chosen because one part shows up in many views: the test bed for finding and going to a ref, and for `sb-c4`, `sb-sequence`, `sb-json` and `sb-erd` working together.
