A software architecture you can walk into, one level at a time.

About

Software systems are built from parts inside parts: a system is made of apps and databases, an app of components. The C4 model draws them one level at a time: who uses the system and what it talks to; then the apps and databases inside it; then the components inside one app. Here you can walk in and out of those levels, with a path at the top showing where you are.

The whole architecture is described once. Every view is drawn from it, and relationships deep inside roll up to the boxes you can see: if a component inside the API calls the mainframe, the overview shows the system calling the mainframe. However far out you are, the lines tell the truth about the detail underneath.

Where it helps

  • Understanding a system from the outside in. Start with who uses it, then open up the part you care about.
  • Seeing what depends on what. Point at a box to light everything it talks to.
  • Explaining a design. The prose can take readers straight to a part, wherever it lives.

Where something else fits better

  • The order things happen in. A sequence diagram shows one request passing from part to part.
  • How data is shaped. An entity relationship diagram shows tables and the fields that link them.
  • A flat set of connected things. A graph, without the levels.

      { id: 'shop', name: 'Shop', kind: 'system', description: 'Sells things online', children: [
        { id: 'web', name: 'Web app', kind: 'container', technology: 'React' },
        { id: 'db', name: 'Orders', kind: 'database', technology: 'PostgreSQL' }
      ] }
    ],
    relationships: [
      { from: 'you', to: 'web', label: 'Shops using' },
      { from: 'web', to: 'db', label: 'Saves orders in', technology: 'SQL' }
    ]
  };
</script>

Kinds are person, system, container, component, database and queue; mark anything outside your own estate external. Relationships can join any two elements, at any depth. Boxes with something inside say so: click "inside", or double-click the box, to go in; use the path, or Escape, to come back out.

Making it reveal, not just display

  • Describe relationships at the level they really happen, between the components that call each other, and let them roll up.
  • Give every box a one-line description of what it's for, not what it is.
  • Take readers there. Call reveal(id) when the prose mentions a part, so the diagram opens the way to it.
  • Use tone for trouble, such as a part that's down or overloaded, so it shows at every level above it too.

The full contract, including every property, method, event and styling hook, is in the manifest.
