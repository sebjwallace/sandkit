What goes with what in a pile of data: the rules it carries, and the samples that break them.

About

Data carries rules nobody wrote down. Every order from Germany is in euros; a product's name and price always come with its code; a refund never arrives without a reason. Finding those rules tells you what the model needs to know, and the few samples that break a rule are often the most interesting thing in the data: a mistake, an edge case, or an exception someone should explain.

This reads every sample and reports which fields determine others, which change together as one thing, which optional fields are present together, and which rules nearly hold, with the samples that break them.

Where it helps

  • Finding a domain's rules. "Country determines currency" is a rule for the model, found rather than guessed.
  • Spotting entities hiding in records. Fields that change together, such as a product's code, name and price, are one thing, and usually want to be modelled as one.
  • Questioning the exceptions. A rule that holds 97% of the time comes with the 3% that don't, named, so someone can go and look.
  • Seeing what a subset is like. Narrow the samples and every rule that appeared, vanished or changed strength is marked.

Where something else fits better

  • What a single field holds. Its values, types and gaps are a profile's job, not this.
  • Rules that hold only sometimes. "When an order is cancelled, it has a refund" is a conditional rule; narrow the samples to cancelled orders and see what appears, or use a tool made for association rules.
  • Small data. With a handful of samples every field seems to decide every other, so rules need enough samples per value to be reported. Below that, read the samples.

Getting started

<script src="components/sb-dependencies/sb-dependencies.js"></script>
<sb-dependencies></sb-dependencies>

<script>
  const deps = document.querySelector('sb-dependencies');
  deps.options = { id: 'orderId' };   // so exceptions name samples by their id
  deps.samples = orders;              // raw samples: it works everything out
  deps.addEventListener('sb-select', (e) => showSamples(e.detail.samples));
</script>

Hand it the samples as they are. Click a near-miss to see its exceptions; clicking an exception's samples tells the sandbox which they are.

An agent can run it too

The same analysis runs from the command line, with no page, so an agent can find a data set's rules before a sandbox exists, near-misses first:

node tools/analyse.mjs dependencies data/ --md --id orderId

What the agent reads and what you see here come from the same function, so they always agree.

Making it reveal, not just display

  • Treat findings as evidence, not truth. A rule seen in the data is an inference until someone confirms it, and an exception is a question until someone explains it. Give them codes in the sandbox's record.
  • Start from the near-misses. They're listed first because they're where the data disagrees with itself.
  • Narrow the samples. A rule that appears within a subset is a rule about that subset: delivered orders ship from their country's warehouse, while returns all go to the hub.
  • Name the id field, so an exception says which samples, and someone can open them.

The full contract, including every property, event and styling hook, is in the manifest.
