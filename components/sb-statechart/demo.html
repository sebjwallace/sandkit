A statechart that shows every state that's active, what can happen now, and what the last step did, in order.

About

Many things behave according to the state they're in: a machine, a protocol, an order, a character in a game. A flat diagram of states soon tangles, so statecharts add three ideas. States can hold other states, so one transition on the outside covers everything inside. Parallel regions let independent parts of a thing each be in their own state at once. History lets a state pick up where it left off. These ideas are powerful, but they make it harder to see where a machine is, and what one event will do to it. This component shows both.

Where it helps

  • Seeing where it is. Every active state is marked: the innermost ones, and every state around them, in each parallel region.
  • Seeing what can happen now. The transitions that would fire are marked, including those inherited from an enclosing state, and those a guard is holding back are crossed out.
  • Seeing what one step did. The states left, the transitions fired and the states entered are numbered in the order they happened, with the actions each ran, on the chart and in words.
  • Seeing what history remembers, beside each history state, and folding a compound state away when its insides don't matter.

Where something else fits better

  • A plain network or a flat machine with a layout of your own. A graph with nodes placed by hand is simpler.
  • A process that runs from start to end, with decisions and lanes for who does what. A flowchart reads better.
  • Many things moving through the same stages, such as orders or tickets. A board of cards in columns shows where they pile up; a statechart shows one thing at a time.

Getting started

<script src="components/sb-statechart/sb-statechart.js"></script>
<sb-statechart sendable></sb-statechart>

<script>
  const chart = document.querySelector('sb-statechart');
  chart.machine = { initial: 'stopped', states: {
    stopped: { on: { PLAY: 'playing' } },
    playing: { initial: 'normal', on: { STOP: 'stopped' }, states: {
      normal: { on: { FF: 'fast' } },
      fast: { on: { FF: 'normal' } }
    } }
  } };
  chart.state = chart.initial();
  chart.addEventListener('sb-send', (e) => { chart.state = chart.next(chart.state, e.detail.event); });
</script>

The machine is written like an XState config: states inside states, on for transitions, type: 'parallel', 'history' or 'final'. You never place anything; it lays itself out. initial() and next() work out where the machine goes, following the statechart rules, and hand back the answer without changing anything.

Two ways to use it

  • The chart is the model. For a concept explained on its own page, or a small model of state beside the main one. Set state from next() on each event, as above. The first example works this way.
  • The model has states of its own. When the sandbox's main model already moves between states, draw them as a machine and set state from the model: where it is, and what it just did. The second example works this way.

Making it reveal, not just display

  • Keep last. The numbered step is the reveal. Pass on what next() returns, or, when mapping a model, say which transitions it took.
  • Feed it the guards. Set guards from the model, so viewers see which transitions are open and which are held back, and why.
  • Put transitions where they belong. One transition on an enclosing state, rather than a copy on every state inside, is what makes a statechart readable, and the chart shows it covering them all.
  • Connect it. Point the prose at states and transitions with highlight, and let sendable turn the chart into the controls.

The full contract, including every property, event and styling hook, is in the manifest.

Examples

A washing machine

The chart is the model here: click an event, below the chart or on it. While running, the wash goes through its cycle as the heater keeps the water warm alongside it. Pausing from any state inside leaves them all, unlocking the door, and the history remembers where both were, so resuming goes straight back. Open the door and starting and resuming are held back.

A pedestrian crossing

Here the model is the junction's own code, keeping time in seconds, and the chart is drawn from it. Traffic and walkers are parallel regions, tied together only by guards: green ends only when someone is waiting, and walking begins only once the cars have stopped. Press the button, let it run, and fold the working state away to see the junction as just working or faulty.
