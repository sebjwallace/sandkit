A behaviour scenario as a card: Given, When, Then, each step pointable.

About

A scenario says how something should behave in one situation: given where things stand, when something happens, then this is what follows. Written as Given, When and Then, it's a statement people can agree on before anyone argues about how it works. This card lays one out to read at a glance: keywords in capitals and lined up so every step's text starts in the same place, And and But tucked under the keyword they carry on, and quoted text and numbers marked as the values a step is about.

Where it helps

  • Pinning down what a model should do. A few scenarios beside the model make its expected behaviour concrete and testable by eye.
  • Comparing situations. Two cards side by side, differing in one step, show exactly what changes the outcome.
  • Walking through cause and effect. Step a scenario through the model and watch each line come true.

Where something else fits better

  • A list of rules a model follows, with the one that just applied: a rules table.
  • A process with branches and loops: a flowchart. A scenario is one path, start to finish.
  • Who sends what to whom: a sequence diagram.

Getting started

Give each card a scenario. Every step can carry a ref, so prose and other views can point at it; the code lights the whole card. See the manifest for the full contract.

card.scenario = {
  code: 'GRID-1',
  title: 'A generator trips',
  steps: [
    { keyword: 'Given', text: 'the grid is running at 50.0 Hz', ref: 'GRID-1.given' },
    { keyword: 'When',  text: 'generator "G2" trips, losing 400 MW', ref: 'GRID-1.when' },
    { keyword: 'Then',  text: 'frequency falls below 49.5 Hz', ref: 'GRID-1.then' }
  ]
};
card.highlight = ['GRID-1.when'];   // a step's ref lights its line; the code lights the card
card.current = 1;                   // the step happening now; later ones fade
card.results = [null, null, { ok: false, actual: 'fell to 49.40 Hz' }];  // from the model

Clicking a step fires sb-select with the step and its index, and changes nothing by itself. The sandbox decides what it means, usually moving the model to that moment and setting current.

Making it reveal, not just state

  • Check it against the model. Have the model play the scenario and set results on every change, with what actually happened where it differs, so turning a knob shows exactly which outcome stops coming true, and what came instead.
  • Tie each step to the model. Clicking a step can show the model at that moment, so the words and the behaviour can be checked against each other.
  • Point from the prose. One phrase can light the same step across several cards, such as the shared starting point, so readers see what scenarios have in common and where they part.
  • Write steps with values. "Frequency falls below 49.2 Hz" says more than "frequency falls", and the value stands out for viewers to find in the model.
  • Keep each card short. A handful of steps, one situation. Split a long one into two.

Examples

A power grid losing a generator

Change the grid and the model checks both scenarios against it. Point at the underlined words to see which steps they mean.

Both scenarios start from the same healthy grid. What differs is how much is lost: a small loss is covered by reserve, a large one sheds load, while hospitals stay connected. Inertia, the spinning mass of the generators, slows the fall: too little and even the small trip goes too far; so much that the large trip no longer sheds load at all.

A railway signal at danger

The same component for a different subject, stepped rather than checked: click a step to mark where the story has got to.

The difference lies in whether the block ahead is clear, and the safety system only acts when a train passes a red signal.
